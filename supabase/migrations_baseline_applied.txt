# Базовая линия истории миграций Supabase
#
# Зачем файл. Долгое время миграции применялись к проду мимо Supabase CLI
# (Lovable, SQL Editor), поэтому таблица учёта supabase_migrations.schema_migrations
# не совпадает с supabase/migrations: часть версий записана без файлов, а часть
# файлов применена без записи. Из-за этого `supabase db push` отказывался
# работать целиком и не применял НИ ОДНОЙ миграции.
#
# Что в файле. Версии локальных миграций, которые фактически уже применены к
# проду, но отсутствуют в учёте. Деплой помечает их как applied — это правка
# только служебной таблицы учёта, схема БД не трогается.
#
# Как проверено (31.08.2026). Для каждой миграции из списка разобраны создаваемые
# ею таблицы и добавляемые колонки, и каждый объект проверен на проде запросом к
# PostgREST. Итог: 22 таблицы и 28 колонок из «хвоста» плюс 18 таблиц и 9 колонок
# из более новых миграций — все присутствуют. Отсутствующий объект даёт
# 404/PGRST205 (таблица) или 400/42703 (колонка) даже на закрытых RLS таблицах —
# проверено отдельно на заведомо несуществующих именах.
#
# Ограничение. Проверка покрывает таблицы и колонки, но не функции, политики,
# индексы, триггеры и кроны внутри тех же файлов.
#
# Как откатить. Пометить нужные версии обратно:
#   supabase migration repair --status reverted <версия>
#
# Новые миграции сюда добавлять НЕ надо — они применяются обычным db push.
