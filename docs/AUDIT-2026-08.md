# Аудит кода MarkVision — август 2026

Проверены: главная и все разделы фронта, CRM и сквозная аналитика, WhatsApp
(Green API + WA Web), реклама Meta и запуск кампаний, Контент-завод и
публикация, все 87 edge-функций, RLS-политики и доступы команды.

Отправная точка: `npm run ci` (lint + typecheck + 433 теста + build) был
**зелёным**. Все дефекты ниже typecheck и тесты не ловили — ошибки PostgREST
и провалы авторизации молча проглатывались (`const { data } = ...` без чтения
`error`), а edge-функции вообще не входят в tsconfig.

## Как искали

1. Прогон `lint` / `typecheck` / `vitest` / `build`.
2. Скрипт сверки всех запросов (`.from().select()`) со схемой БД — ищет
   обращения к несуществующим таблицам и колонкам (молчаливые 400).
3. Скрипт «проигрывания» всех миграций по порядку с учётом
   `CREATE POLICY` / `DROP POLICY` — чтобы получить **итоговое** состояние RLS,
   а не то, что написано в отдельно взятом файле.
4. Чтение критичных путей: авторизация, деньги, публикация, вебхуки.

### Доступы команды — итог проверки

Проверено отдельно, как просили. Итоговое состояние **корректное**:

- `user_can_access_project` = админ **ИЛИ** владелец проекта **ИЛИ** строка в
  `project_members` **именно по этому проекту**. Опасная промежуточная версия
  (доступ ко всем проектам при наличии любой строки в `team_member_modules`)

- `project_members` пишет только админ или владелец проекта.

Исправлены перекосы: `events`, `tasks`, `communications` (см. S4 и F7).

### 1. RLS выключен в «клиентском» проекте — ВЫСОКИЙ приоритет

`supabase/migrations_client_config/004_full_schema.sql:186` содержит
`disable row level security` на таблицах:

- `clients_secrets` — `fb_token`, `wa_api_token` (токены доступа);
- `clients_config` — `fb_token`, `wa_api_token`, `pixel_id`;
- `leads_crm` — телефоны, IP, user-agent, fbclid (персональные данные);
- `leads`, `wa_clicks`, `ad_conversations` и остальные.

При выключенном RLS PostgREST полагается только на GRANT'ы, а Supabase по
умолчанию выдаёт роли `anon` полный доступ. Комментарий в файле («фронт пишет
только через service_role-эквивалент») не соответствует коду:
`src/integrations/clientConfig/client.ts` ходит туда публикуемым ключом прямо
из браузера.

**Что нужно сделать вам:** сказать, развёрнут ли ещё отдельный клиентский
Supabase-проект (в `.env.production` сейчас `VITE_CLIENT_SUPABASE_URL`
указывает на основной `szfgdruhlebfvcmlvxdk`, то есть отдельного проекта может
уже не быть).

- Если проект **не используется** — его надо удалить/заархивировать, и вопрос
  закрыт.
- Если **используется** — пришлите его ref, я подготовлю миграцию: включить
  RLS на всех перечисленных таблицах и оставить доступ только `service_role`.

Проверить, открыты ли данные, можно одной командой (подставьте URL и anon-ключ
того проекта):

```bash
curl -s "https://<ref>.supabase.co/rest/v1/clients_secrets?select=client_id&limit=1" \
  -H "apikey: <anon-key>"
```

Пустой массив `[]` или ошибка — доступа нет, всё в порядке. Если вернулись
строки — таблица с токенами открыта наружу.

### 3. Легаси-воронки видны всем проектам — НИЗКИЙ приоритет, нужен ответ по данным

Политика `pipelines_select_scoped` разрешает читать воронки с
`project_id IS NULL` любому авторизованному пользователю. Закрывать вслепую
нельзя: если какой-то проект до сих пор работает на такой воронке, у него
пропадут этапы в CRM.

**Что нужно сделать вам:** выполнить в SQL Editor и прислать результат —

```sql
select count(*) as null_pipelines from public.pipelines where project_id is null;
select count(*) as leads_on_null_pipelines
  from public.leads l
  join public.pipelines p on p.id = l.pipeline_id
 where p.project_id is null;
```

Если по обоим запросам `0` — я закрою политику миграцией.

## Осталось: что могу доделать сам (по вашей команде)

   дефект, а недостающая функция — скажите, нужна ли.

## Известное поведение (не дефект)

- **Дневной лимит рассылки считается по UTC.** И запись
  (`broadcast_bump_daily`), и чтение используют UTC-дату — они согласованы,
  но счётчик обнуляется в 05:00 по Алматы, а не в полночь. Менять можно, но
  на дне переключения счётчик сбросится повторно и суточный потолок
  фактически удвоится — а это риск бана номера в WhatsApp. Трогать без
  необходимости не советую.
