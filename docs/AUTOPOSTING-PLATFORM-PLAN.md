# Платформа автопостинга: план реализации

**Суть системы.** Радар собирает идеи и сценарии конкурентов и рынка → банк идей → существующие движки MarkVision делают из идеи видео → согласование → библиотека готового контента → дистрибуция по официальным API в десятки и сотни аккаунтов площадок → метрики возвращаются в радар и переоценивают идеи. Один проект MarkVision = один клиент, у которого может быть 100+ аккаунтов.

**Дата:** 4 сентября 2026. **Основа:** аудит репозитория `markvision-a1` и живых n8n-воркфлоу.

## 1. Резюме

Три из пяти слоёв уже существуют в коде, но не соединены между собой:

| Слой | Состояние | Что есть | Чего нет |
|---|---|---|---|
| Радар (идеи конкурентов) | **только n8n, без схемы в git** | воркфлоу «Мониторинг конкурентов» (Apify → Gemini → сценарий → таблица `content_factory`), «Разбор контента (Сайт) v3» (разбор креатива по ссылке из Telegram), `pipeline/download.py` + `reference.py` (ремейк референса), Ad Library engine | таблиц `competitors`/`competitor_posts` в миграциях нет, UI нет, скоринга нет, Apify-токен захардкожен в URL ноды |
| Генерация контента | **готово, 4 движка** | контент-конвейер (тема → сценарий → HeyGen → согласование), Reels faceless (ElevenLabs + Remotion), монтаж съёмки, Контент-завод креативов | движки не пишут в библиотеку публикации `publish_videos`; вариантов под группы аккаунтов нет |
| Библиотека и согласование | **частично** | `content_assets`, `content_reviews`, Telegram-кнопки; `publish_videos.caption_variants` | нет автоматической передачи одобренного ролика в дистрибуцию |
| Дистрибуция | **готово для Instagram, без UI** | `publish_accounts/videos/jobs/logs/groups`, очередь `claim_publish_jobs` (SKIP LOCKED), воркер, монитор токенов и ошибок, OAuth Meta, шифрование токенов | TikTok/YouTube/Threads — заглушки; стратегия групп записана, но не читается; drip без джиттера, часовых поясов и разгона; нет страницы аккаунтов; нет обновления long-lived токенов |
| Аналитика и обратная связь | **частично** | `instagram-sync` (reach, views, saves, shares) для одного аккаунта проекта, страница ContentAnalytics | нет метрик по `external_post_id` всех аккаунтов, нет связи «идея → результат» |

Главный вывод: **узкое место не в пропускной способности API, а в контенте и правилах площадок.** 100 аккаунтов по 1–2 публикации в день = 100–200 публикаций в сутки ≈ 8 в час — существующий воркер справится. Дорого и рискованно другое: сделать 100–200 *разных* роликов в день и не превратить сеть аккаунтов в спам-паттерн. Поэтому план строится вокруг **групп аккаунтов с собственной нишей/персоной** и **фабрики вариантов**, а не вокруг «одно видео во все 100».

## 2. Границы и правила (не обсуждаются на уровне реализации)

1. **Только официальные API площадок**: Instagram Content Publishing API, Threads API, TikTok Content Posting API, YouTube Data API. Никакой браузерной автоматизации, Multilogin/VNC не входит в контур — это уже зафиксировано в `docs/PUBLISHING-SYSTEM.md`.
2. **Аккаунты принадлежат клиенту и подключаются через OAuth** (Meta OAuth уже есть). Платформа не хранит пароли и не «фармит» аккаунты.
3. **Исследование — по публичным данным через лицензированных провайдеров и официальные API**: Meta Ad Library API, Instagram Graph `business_discovery` и hashtag search, ScrapeCreators/Apify (уже оплачены). Храним разбор и метрики, а не копии чужих видео для перезалива.
4. **Вариативность — редакционная, а не техническая.** Разные группы аккаунтов получают разные сценарии, персоны, голоса и подписи потому, что у них разная аудитория. Уникализация файлов «для обхода детекции» не делается.
5. **Лимиты площадок соблюдаются кодом, а не оператором**: Instagram API — 25 публикаций на аккаунт за 24 ч (в коде уже классифицируется код ошибки 9007); Threads — 250 постов/сутки; TikTok — до прохождения аудита приложения публикации только приватные; YouTube — квота 10 000 единиц/день на проект Google Cloud (≈6 загрузок) до расширения квоты. Цифры проверить при реализации соответствующего publisher.
6. **Согласование остаётся**: автопубликация без ворот только для групп, которые клиент явно перевёл в режим «доверенная».

Секреты только в Supabase Secrets и нодах «Настройки».

## 4. Модули

### M1. Радар идей

**Цель:** каждое утро у проекта есть ранжированный список идей с источником, хуком, структурой и оценкой, из которого одна кнопка делает тему в контент-плане.

**Данные (новая миграция `radar`)**

| Таблица | Назначение |
|---|---|
| `radar_sources` | что мониторим: `project_id`, `kind` (competitor_account / hashtag / ad_library_query / own_account), `platform`, `handle_or_query`, `enabled`, `crawl_interval_hours`, `last_crawled_at` |
| `radar_posts` | собранные публикации: `source_id`, `platform`, `external_id` (unique с platform), `url`, `published_at`, `media_type`, `caption`, `transcript`, `metrics jsonb` (likes, comments, views, shares, follower_count на момент сбора), `engagement_rate`, `velocity` (прирост за 24/72 ч), `raw jsonb`, `analysis jsonb` (hook, structure, triggers, niche, score), `analyzed_at` |
| `idea_bank` | идеи: `project_id`, `title`, `hook`, `angle`, `script_draft`, `source_post_ids uuid[]`, `score`, `status` (new / approved / used / rejected), `target_group_id` (группа аккаунтов), `content_item_id` (когда ушла в план), `outcome_score` (заполняет аналитика) |
| `radar_runs` | журнал сборов: `source_id`, `provider`, `items`, `cost_usd`, `error` |

**Сервисы**

- Edge-функция `radar` (подписанный callback по образцу `content-pipeline/internal/callback`): `ingest` (upsert постов по `platform+external_id`), `analyze` (Whisper-транскрипт при наличии видео → LLM-разбор по фиксированной JSON-схеме: hook / problem / solution / CTA / triggers / niche / score), `score` (пересчёт engagement_rate = interactions / followers, velocity), `promote` (идея → `content_plan_items` REELS `idea` с `prompts` = хук и структура; дальше работает контент-конвейер).
- n8n: переработать «Мониторинг конкурентов» — писать в `radar_posts` вместо `content_factory`, вынести Apify-токен из URL ноды в credentials (**сейчас он захардкожен — ротировать немедленно**), добавить провайдер ScrapeCreators (дешевле для одиночных постов) и Meta Ad Library API как отдельный источник. «Разбор контента (Сайт) v3» становится ручным входом радара: ссылка из Telegram → `radar_posts` + `idea_bank`.
- Собственные метрики: `instagram-sync` расширяется на все аккаунты `publish_accounts` проекта (сейчас один аккаунт), результаты — в `radar_posts` с `kind = own_account`, чтобы «что работает у нас» участвовало в скоринге.

**UI:** страница «Радар» в разделе Маркетинг: источники (добавить конкурента/хештег), лента постов с оценкой, банк идей с фильтрами по нише/группе и кнопкой «В контент-план → группа X». Существующая карточка темы получает блок «Источник идеи».

**Стоимость:** Apify instagram-scraper ≈ $2–3 за 1000 постов; Whisper ≈ $0.006/мин; LLM-разбор ≈ $0.002–0.01 за пост. 20 конкурентов × 10 постов/день ≈ $1–3/день на проект.

### M2. Генерация и фабрика вариантов

**Цель:** из одной одобренной идеи получить N роликов под N групп аккаунтов, не N раз запуская всё с нуля.

- Единая точка входа уже есть — `content_plan_items` + контент-конвейер (`docs/CONTENT-PIPELINE.md`). Добавляется поле `engine` (heygen / reels_faceless / montage) и `target_group_id`.
- **Фабрика вариантов** — новая таблица `content_variants`: `content_item_id`, `group_id`, `persona` (аватар/голос HeyGen или голос ElevenLabs), `script_variant` (LLM переписывает сценарий под персону и угол группы, проверка теми же правилами 90–130 слов), `caption_variant`, `state`. Каждый вариант = отдельный `pipeline_run` того же конвейера, лимит `max_parallel_videos` и бюджет уже работают.
- Faceless-движок (Reels) закрывает дешёвые варианты: один сценарий → разные темы оформления (8 тем `remotion/src/themes.ts`) и голоса — без HeyGen-минут.
- После `approved` конвейер сам вызывает `publish-intake` `video_ready` c `source = content_pipeline`, `source_ref = content_asset_id` — этот шов (`publish_videos.source/source_ref`) уже спроектирован, но пока ничем не заполняется.

**Экономика вариантов (ориентир):** HeyGen ≈ $1–2 за минуту готового видео. 100 аккаунтов в 10 групп, по 1 уникальному ролику на группу в день = 10 рендеров ≈ $15–30/день; faceless-варианты — копейки (TTS ≈ $0.2–0.5 на ролик). Один ролик на все 100 аккаунтов дешевле, но это и есть спам-паттерн — не делаем.

### M3. Дистрибуция на 100+ аккаунтов

**Цель:** аккаунты клиента подключаются пачкой, получают персону и группу, публикации раскладываются по времени с учётом лимитов, разгона и здоровья аккаунта; сбои видны агрегированно.

**Модель аккаунта** (расширение `publish_accounts`): `group_id`, `persona_id`, `timezone`, `posting_window` (например 09:00–21:00 локального времени), `ramp_stage` и `ramp_started_at` (разгон частоты: 1 публикация/день первые 7 дней → 2 → до целевого `daily_limit`; это правило частоты, а не «прогрев» действиями), `health_score` (успешные публикации, ошибки, `limited`, возраст токена), `token_refreshed_at`.

**Планировщик слотов** вместо drip по индексу: `publish_slots` (`account_id`, `slot_at`, `job_id`) строится функцией `plan_publish_slots(video_id, group_id)`: для каждого аккаунта берётся следующее свободное окно в его часовом поясе, джиттер ±20 мин, минимальный интервал между публикациями аккаунта, глобальный лимит площадки на проект, разгон. Стратегия группы (`publish_strategy`, `per_hour`) начинает читаться в `publish-intake` (сейчас записана и мертва).

**Воркер:** сохранить `claim_publish_jobs`, но убрать O(N) подсчёт дневного лимита (счётчик `published_today` + дата на аккаунте, сброс по локальной полуночи) и запускать воркер параллельно: pg_cron ежеминутно × 3 партиции (`worker_id`, `p_batch` 25) или Node-демон на VPS (`scripts/publish-daemon.mjs` по образцу `montage-daemon.mjs`) для длинных загрузок YouTube/TikTok, которым не хватает 45 с edge-функции.

**Publishers:** Threads (двухшаговая публикация, самый простой) → YouTube (`videos.insert`, resumable upload с VPS, квота) → TikTok (`PULL_FROM_URL` с верифицированного домена, аудит приложения — заложить 3–6 недель ожидания). Meta: обновление long-lived токенов раз в 50 дней в `publish-monitor mode:tokens`.

**Наблюдаемость:** витрина `publish_metrics` (очередь, публикаций/час, ошибки по кодам, аккаунты по статусам, возраст токенов), Telegram-дайджест раз в час вместо сообщения на каждый сбой (сейчас runner шлёт по каждому), алерты только на `error`-аккаунты и остановку очереди.

**UI:** страница «Аккаунты»: подключить пачкой (OAuth → `available` → `connect page_ids[]` уже есть), таблица со статусом/здоровьем/лимитом, группы и персоны, кнопка «Залить видео в группу», лента заданий с фильтрами и повтором.

**Мощность:** при 100 аккаунтах × 2 публикации = 200/сутки ≈ 8–9/час; при 1000 аккаунтах — 80–90/час, что всё ещё в пределах одного VPS-демона. Ограничитель — количество *уникальных* роликов (см. M2) и аудит TikTok/YouTube.

### M4. Согласование и управление

- Режимы группы: `review_required` (кнопки в MarkVision/Telegram, уже есть), `auto_publish` (для доверенных групп после N подряд одобренных роликов), `paused`.
- Бюджеты на проект переносятся из `content_pipeline_settings` в общий `project_budgets`: HeyGen-минуты, TTS, Apify, LLM — дневной и месячный потолок, `budget_ok()` проверяется радаром, конвейером и планировщиком.
- Роли: оператор клиента видит только свой проект (RLS уже такая), менеджер MarkVision — все.
- Аварийная кнопка «стоп» на проект и на группу (`publish_enabled=false` пачкой) — есть на уровне таблицы, нужен UI.

### M5. Аналитика и обратная связь

- `post_metrics` (`account_id`, `external_post_id`, `captured_at`, reach, views, likes, saves, shares, comments) — сбор для всех аккаунтов проекта через Graph API (Instagram/Threads) и Data API (YouTube) по расписанию 1, 3, 7 дней после публикации.
- Связь `publish_jobs → publish_videos → content_item → idea_bank`: `outcome_score` идеи = медиана нормированного охвата по группе. Радар поднимает похожие идеи/хуки выше; отчёт «что залетело» по неделе в Telegram.
- Дашборд «Сеть»: аккаунты, публикации, охват по группам, лучшие хуки, стоимость на 1000 просмотров.

Всё — идемпотентными миграциями в `supabase/migrations/`, с RLS `user_can_access_project`, записью только через service_role, RPC очередей с `REVOKE ... FROM anon, authenticated`.

Оценки — для одного backend/frontend-разработчика плюс оператор n8n; сроки последовательные, этапы 2 и 3 можно вести параллельно двумя людьми.

| Этап | Срок | Результат | Критерий приёмки |
|---|---|---|---|
| **0. Стабилизация** | 1 нед | ротация захардкоженного Apify-токена и cron_secret из миграции; боевой smoke test контент-конвейера (`scripts/content-pipeline-smoke.mjs e2e`); страница «Аккаунты» (список, подключение, статус) поверх `publish_accounts_safe`; `publish-intake` читает стратегию группы | 5 аккаунтов подключены через UI, одно видео ушло в группу drip, дайджест в Telegram |
| **1. Радар v1** | 2–3 нед | миграция `radar`; edge `radar` (ingest/analyze/score/promote); n8n «Мониторинг конкурентов v2» пишет в `radar_posts`; страница «Радар» и банк идей; «В контент-план» | 20 конкурентов, ежедневный сбор, ≥10 идей/день с оценкой; идея становится темой и проходит конвейер без ручных правок |
| **2. Связка и варианты** | 2 нед | `approved` → `publish_videos` автоматически; `content_variants` + `personas`; faceless-вариант через Reels-движок; `engine` на теме | одна идея → 3 группы → 3 разных ролика → 3 записи `publish_videos` без участия оператора |

Дистрибуция 100+** | 3 нед | планировщик слотов, разгон и здоровье, параллельный воркер/демон, обновление токенов Meta, Threads-publisher, дайджест вместо поштучных алертов; заявка на аудит TikTok и квоту YouTube — в первый день этапа | 100 аккаунтов (тестовых/клиентских) получают 1–2 публикации в день в своих окнах, 0 нарушений лимитов по логам, очередь пуста к концу дня |

Итого **12–14 недель** до промышленной версии на Instagram + Threads; TikTok и YouTube — по готовности аудита (внешний срок).

## 7. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Площадка ограничивает сеть аккаунтов за однотипный контент | высокая при «одно видео везде» | группы с персонами, фабрика вариантов, разгон частоты, health_score, автопауза группы при росте `limited` |
| Аудит TikTok/квота YouTube затягиваются | высокая | подать заявки на этапе 3, день 1; до одобрения — Instagram + Threads |
| Стоимость HeyGen при 100+ уникальных роликах/день | средняя | faceless-варианты для большинства групп, бюджеты `project_budgets`, HeyGen только для «лицевых» групп |
| Провайдеры скрапинга меняют формат/цену | средняя | `radar_runs` с cost, два провайдера с фолбэком (уже в `download.py`), сырое `raw jsonb` |
| Токены аккаунтов протухают массово | средняя | обновление long-lived токенов по расписанию, `token_expired` → уведомление владельцу аккаунта, а не оператору |
| Секреты в n8n (Apify-токен в URL, cron_secret в миграции) | факт | ротация на этапе 0, credentials n8n, `PASTE_…` в экспортах |
| Юридические претензии по чужому контенту | низкая при соблюдении §2 | храним разбор и метрики, не перезаливаем чужие видео; ремейк — только своя съёмка по структуре референса |

## 8. Что нужно решить заказчику до старта

1. **Стратегия сети**: сколько групп и какие персоны/ниши; одна группа = одна тема, а не один клиент на 100 клонов.
2. **Владение аккаунтами**: клиент подключает свои Business/Creator-аккаунты через OAuth; аккаунты без Facebook-страницы подключить нельзя.
3. **Площадки первой очереди**: Instagram + Threads сразу; TikTok и YouTube — после аудита (заявки подаём мы).
4. **Бюджеты**: месячный потолок на HeyGen-минуты, TTS и сбор данных; при исчерпании конвейер останавливается сам.
5. **Режим согласования**: всё через ворота или доверенные группы с автопубликацией.
