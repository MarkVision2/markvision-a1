# Контент-завод без n8n: генерация статичного контента напрямую

Как «Создать дизайн» в Контент-заводе работает теперь: заявка не уходит в n8n,
а встаёт в очередь, картинки генерирует Gemini из наших edge-функций, результат
приходит в «Созданный контент» через realtime, дублируется в Telegram и
автоматически удаляется через неделю.

**Сам n8n не тронут.** Воркфлоу остались как есть; их логика прочитана
и перенесена. Откат на прежний путь — одна переменная, без правок кода.

---

## 1. Как было

```
CreateStep3 → edge content-factory-proxy → n8n webhook/clony-yurii
                                             (workflow «Clony AI», 87 нод)
                                                       ↓
                              content_factory_results (INSERT service_role)
                                                       ↓ realtime по request_id
                                             CreateStep3 подменяет карточку
```

Фронт ждал ответа n8n до 120 секунд и часто ловил таймаут, хотя генерация шла.

## 2. Что делал воркфлоу

Оригинал (`dCQ20aXv6B9LRjDe`) нашему n8n-токену недоступен — он в другом проекте.
Но в том же инстансе есть его рабочий клон **«Даяна Сontent ЗАВОД»**
(`6pnv6NrDkbwyCflT`, 87 нод), и разбор сделан по нему:

| Этап | Ноды n8n | Что происходит |
|------|----------|----------------|
| Приём | `Webhook` | тело заявки: `content_type`, `prompt`, `image_urls`, `style`, `color`, `slides`, `request_id`… |
| Анализ входа | `Analyze image1` (Gemini Vision), `Analyze audio`, `Scrape using HTML API` (ScrapingBee), `Run an Actor` (Apify) | описание референсного фото, расшифровка аудио, текст сайта по ссылке |
| Контекст | `image` (Set) | собирает `all_data` — весь бриф JSON-ом без служебных полей |
| Маршрутизация | `Switch1` по `body.content_type` | ветки `fb-target`, `insta-carousel`, `instagram-stories`, `neuro-photo`, остальное — общая |
| Стратегия | `chainLlm` в каждой ветке | свой промпт → JSON со списком слайдов (`image_prompt`, `slide_type`, `aspect_ratio`) |
| Разбор | `Parse Strategy` (code) | терпимый парсер: снимает ```json, чинит висячие запятые, ищет массив под разными именами |

| Публикация | `Upload an asset` (Cloudinary) → `AI DESIGN Save All` (Supabase) → `Send a photo message` (Telegram) | картинка в CDN, строка в `content_factory_results`, фото в чат |

## 3. Как стало

```
CreateStep3 → edge content-factory-generate ──► content_factory_jobs (queued)
                  (JWT, мгновенный ответ)              │
                          └── fire-and-forget ─────────┤
   pg_cron */1 ──────────────────────────────────► content-factory-worker
                          (страховка, ретраи)          │
                                                       ▼
        анализ входа → промпт ветки → стратегия → кадр за кадром:
        Gemini image → Storage → content_factory_results → галерея → Telegram
                                                       │
                                             realtime по request_id
                                                       ▼
                                        «Созданный контент» в мастере
```

Ключевое отличие: **фронт больше ничего не ждёт**. Приёмник ставит задание
и отвечает сразу; карточки заполняются по мере готовности кадров — ровно тем
же realtime-каналом, что и раньше.

### Карта файлов

| Файл | Роль |
|------|------|
| `supabase/functions/_lib/contentFactoryPrompts.ts` | промпты веток и vision-анализа, перенесённые из n8n **дословно** |
| `supabase/functions/_lib/contentFactoryGen.ts` | подстановка `{{токенов}}`, порт `Parse Strategy v3.0`, сборка промпта кадра |
| `supabase/functions/_lib/geminiParse.ts` | разбор ответа Gemini и тело запроса на генерацию (чистое, под тестами) |
| `supabase/functions/_lib/gemini.ts` | клиент моделей Google: прямой Google API или Lovable AI Gateway |
| `supabase/functions/_lib/safeUrl.ts` | проверка ссылок перед серверным запросом (SSRF) |
| `supabase/functions/_lib/mediaHosts.ts` | allowlist хранилищ для референсных фото |
| `supabase/functions/_lib/kie.ts` + `kieParse.ts` | клиент kie.ai: createTask → опрос → скачивание кадра |
| `supabase/functions/content-factory-generate/index.ts` | приём заявки вместо вебхука в n8n |
| `supabase/functions/content-factory-worker/index.ts` | конечный автомат генерации |
| `supabase/migrations/20260901100000_content_factory_direct.sql` | очередь, уникальность слайда, кроны воркера и очистки |
| `src/lib/contentFactory.ts` | переключатель контура на фронте |

### Промпты перенесены дословно

Формулировки подбирались на живых генерациях — вольная переработка меняет
результат. Тронуты только подстановки: выражения n8n
(`$item("0").$node["image"].json["style"]`) заменены на токены `{{style}}`,
которые подставляет `renderPrompt`. Тест проверяет, что в перенесённых текстах
не осталось ни одного выражения n8n.

### Что сделано иначе, чем в n8n

- **Cloudinary не используется** — картинки лежат в Supabase Storage
  (`content-factory/generated/<request_id>/<n>.png`). Одним внешним сервисом
  и одним ключом меньше.
- **ScrapingBee и Apify не используются** — текст страницы по ссылке
  вытягивается обычным `fetch` с вырезанием тегов. Для контекста модели этого
  достаточно; если понадобится качественный скрейпинг, это отдельный шаг.
- **Аудио не анализируется** — в Контент-заводе его нет, поле `audio_url`
  мастер и раньше не заполнял.
- **Кадры генерируются по одному** с мягким дедлайном: если время вызова
  подходит к концу, задание возвращается в очередь и крон продолжает со
  следующего кадра. Карусель на десять слайдов не упирается в лимит функции.
- **Отказ фильтра на одном кадре не роняет остальные** — этот слайд помечается
  ошибкой, генерация продолжается.

### Ключ: новый не нужен

Достать ключ Google из n8n нельзя — он хранится там зашифрованным, и API
credentials наружу не отдаёт (MCP умеет только искать, читать и запускать
воркфлоу). Единственный способ его вытащить — завести в n8n воркфлоу, который
сам выдаст ключ наружу, а n8n договорились не трогать.

Этого и не потребовалось: в проекте уже настроен **Lovable AI Gateway**
(`LOVABLE_API_KEY`, им пользуются функции `ai-rop-*` и `content-scheduler`),
а он проксирует те же модели Google. Поэтому клиент умеет два пути:

Провайдеры разделены: **картинки** и **текст** выбираются независимо, потому
что kie.ai умеет только картинки.

| Роль | Провайдер | Ключ | Модель по умолчанию |
|------|-----------|------|---------------------|
| Картинки | **kie.ai** (1-й) | `KIE_API_KEY` | `google/nano-banana` |
| Картинки | Прямой Google (2-й) | `GEMINI_API_KEY` | `gemini-3-pro-image-preview` — как в n8n |
| Картинки | Lovable Gateway (3-й) | `LOVABLE_API_KEY` | `google/gemini-2.5-flash-image-preview` |
| Текст и зрение | Прямой Google (1-й) | `GEMINI_API_KEY` | `gemini-pro-latest` |
| Текст и зрение | Lovable Gateway (2-й) | `LOVABLE_API_KEY` | `google/gemini-2.5-flash` |

Порядок переопределяется явно: `CONTENT_FACTORY_IMAGE_PROVIDER` и
`CONTENT_FACTORY_TEXT_PROVIDER` (значения `kie` / `google` / `gateway`).
Это нужно как раз в ситуации «ключ Google задан, но без квоты»: картинки идут
в kie.ai, а текст — на шлюз, и удалять ключ ради этого не приходится.

### Почему kie.ai впереди Google

Проверено живыми запросами на двух ключах Google: аутентификация проходит
(список моделей отдаётся), но любой `generateContent` возвращает 429
`RESOURCE_EXHAUSTED` с `limit: 0` — модели генерации на бесплатном плане
недоступны в принципе, а не «квота кончилась».

Бонусом $300 это не лечится: **с 2 марта 2026 Google исключил Gemini API
и AI Studio из программы free trial** — welcome-кредиты, выданные после этой
даты, на них не тратятся. Нужен prepaid-баланс. kie.ai перепродаёт те же
модели заметно дешевле и по обычному ключу, поэтому он и стоит первым.

Случай нулевой квоты распознаётся отдельно (`classifyQuotaError`): задание
не уходит в получасовой цикл ретраев, а сразу пишет в статус, что нужно
включить оплату. Имена моделей везде переопределяются переменными окружения —
preview-модели Google периодически переименовывает.

### Как устроен kie.ai

API асинхронный, и это ложится на очередь почти без швов:

```
POST /api/v1/jobs/createTask   {model, input:{prompt, image_size, image_urls}}
   → {code:200, data:{taskId}}
GET  /api/v1/jobs/recordInfo?taskId=…
   → {data:{state: waiting|queuing|generating|success|fail, resultJson:"{\"resultUrls\":[…]}"}}
```

`taskId` сохраняется в задании (`analysis.task_<index>`). Если кадр не успел
за отведённое время, задание возвращается в очередь **без траты попытки**,
и следующий проход крона продолжает опрос той же задачи — а не создаёт
и не оплачивает новую. Референсы уходят ссылками: наши фото и так лежат
в публичном Storage, перекодировка не нужна.

Готовый кадр скачивается по ссылке из ответа. Allowlist пользовательских
хранилищ тут не применяется — ссылка пришла от сервиса, к которому мы сами
обратились, — но внутренние адреса всё равно закрыты (`isPublicHttpUrl`).

**Не проверено вживую:** домен `api.kie.ai` закрыт сетевой политикой среды,
поэтому контракт взят из документации, а разбор ответов сделан терпимым —
проверяются оба правдоподобных места результата и обе формы записи состояний.
Первая живая генерация покажет, попал ли разбор.

## 3.1 Разбор безопасности и повторное чтение

После первого прохода код перечитан отдельно. Найдено и исправлено четыре вещи:

**1. SSRF через референсные фото.** `image_urls` приходит от клиента, а качает
ссылки сервер — проверка была только на `https://`. Теперь работает allowlist
хранилищ (`_lib/mediaHosts.ts`): мастер и так заливает фото в Storage перед
отправкой, чужой адрес там означал бы попытку достучаться до внутренней сети.
Список расширяется через `CONTENT_FACTORY_MEDIA_HOSTS`.

**2. SSRF через ссылку на страницу товара.** Здесь allowlist не подходит —
человек указывает свой сайт, это любой домен. Закрыты внутренние адреса
(`_lib/safeUrl.ts`: localhost, `.internal`, IP-литералы во всех формах записи,
включая `2130706433` и `0x7f000001`), а редиректы разбираются вручную: иначе
внешний сайт увёл бы нас в локальную сеть уже после проверки.

**3. Дубли в галерее.** Воркер вставлял карточку на каждый кадр, а мастер по
realtime писал туда же свою — для карусели получались лишние записи поверх.
Галерея хранит одну карточку на заявку (так устроен уникальный индекс
`project_id, request_id`), поэтому воркер сохраняет только первый удавшийся
кадр под тем же `request_id`, а конфликт с записью мастера считает штатной
гонкой, а не сбоем.

**4. Зависшие карточки.** Приёмник создаёт заглушки по числу кадров из брифа,
но модель может вернуть меньше — лишние строки висели бы «в работе» вечно.
Теперь они удаляются, как только известна стратегия.

## 4. Автоудаление

Просьба была, чтобы созданный контент не копился. Сроки сокращены:

| Что | Было | Стало |
|-----|------|-------|
| `content_factory_gallery` | 30 дней | **7 дней** |
| `content_factory_results` | 14 дней | **3 дня** |
| `content-factory-uploads/requests/` (референсы) | 14 дней | **7 дней** |
| `content_factory_jobs` | — | **7 дней** (только завершённые) |

Чистит функция `cleanup_content_factory_data` — меньше этих значений она не
примет (защита от случайного «удалить всё»).

### Почему очистку пришлось чинить, а не только ускорить

Механизм существовал и до этой работы, но не отработал ни разу. Единственным
его запуском был еженедельный GitHub Actions, а тот падал на самой первой
строке: секрет `CONTENT_FACTORY_CLEANUP_KEY` в репозитории не задан. Все 13
запусков с 7 июня по 30 августа 2026 — `failure` с `CONTENT_FACTORY_CLEANUP_KEY
missing`, до базы дело не доходило. То есть контент не удалялся вообще.

Поэтому очистка перевешена на кроны в самой БД, которым чужие секреты не нужны:

| Крон | Время (UTC) | Что делает |
|------|-------------|-----------|
| `content-factory-cleanup-daily` | 03:00 | галерея и `results` — чистым SQL |
| `content-factory-jobs-cleanup-daily` | 03:20 | завершённые задания очереди |
| `content-factory-storage-cleanup-daily` | 03:40 | файлы в Storage, через edge-функцию |

Файлы из SQL не удалить, поэтому третий крон ходит в `content-factory-cleanup`.
Чтобы ему не понадобился недостающий секрет, функция теперь принимает и
`x-automation-key` (= `automation_settings.cron_secret`) — тот же ключ, которым
БД дёргает остальные кроны. Прежний `x-cleanup-key` продолжает работать.

`cleanup_content_factory_data` объявлена в ручном наборе
(`migrations_client_config/009`), который `db push` не применяет. Крон хранит
текст команды и не проверяет его при постановке, поэтому отсутствие функции
обернулось бы молчаливым падением каждую ночь — ровно тем же классом отказа,
что и выше. Миграция повторяет объявление у себя (как `20260606160000`
повторяет таблицы галереи из `007`), а тест `contentFactoryCleanupSql.test.ts`
следит, чтобы копии не разъехались.

GitHub Actions по воскресеньям остаётся страховкой и ручной кнопкой
(`.github/workflows/content-factory-cleanup.yml`). Чтобы он заработал, нужен
секрет `CONTENT_FACTORY_CLEANUP_KEY` в настройках репозитория — но очистка
больше от него не зависит.

## 5. Telegram

Кадр уходит в чат проекта: `telegram_links.chat_id` по `project_id` — та же
связка, что использует монтаж. Если проект не привязан, берётся
`CONTENT_FACTORY_TELEGRAM_CHAT_ID`; если нет и его, отправка молча
пропускается и на генерацию это не влияет.

## 6. Как включить

1. **Применить миграцию** `20260901100000_content_factory_direct.sql`.
   Она заодно схлопывает дубли в `content_factory_results` — они могли
   накопиться, потому что прежний контур писал строки без уникального ключа.
2. **Задеплоить функции**: `content-factory-generate`, `content-factory-worker`
   и `content-factory-cleanup`. `verify_jwt = false` для воркера прописан в
   `supabase/config.toml`. Очистку передеплоить обязательно: у неё изменилась
   авторизация, и без этого ночной крон очистки Storage будет получать 401.
3. **Секреты**:
   - `KIE_API_KEY` — картинки через kie.ai. Рекомендуемый путь: дешевле
     и не требует prepaid-баланса Google.
   - `CONTENT_FACTORY_TEXT_PROVIDER=gateway` — если `GEMINI_API_KEY` задан,
     но у него нет квоты: текст тогда пойдёт через уже настроенный
     `LOVABLE_API_KEY`, а картинки — через kie.ai.
   - `GEMINI_API_KEY` — нужен, только если у проекта Google включена оплата.
     Если ни одного ключа нет, приёмник честно отвечает 503, а не копит
     задания, которые некому выполнить.
   - `TELEGRAM_BOT_TOKEN` — уже есть.
   - `CONTENT_FACTORY_TELEGRAM_CHAT_ID` — необязательный запасной чат.
4. **Фронт**: по умолчанию идёт прямой контур. Откат — `VITE_CONTENT_FACTORY_MODE=n8n`.
5. **Проверить на одном стиле**: сгенерировать один креатив и сверить с тем,
   что даёт n8n на том же брифе.

## 7. Что осталось непроверенным

- **Оригинальный воркфлоу не прочитан** — только его клон. Ветки `Switch1` в
  клоне те же четыре, но если в оригинале правили промпты после расхождения
  копий, результат будет отличаться. Сверяется первой генерацией.
- **Формат ответа шлюза** — картинку он отдаёт data-URL-ом, но точное место
  зависит от версии: разбор проверяет `message.images[]`, мультимодальный
  `content[]` и data-URL прямо в тексте. Все три ветки под тестами, но какая
  сработает на живом ответе, покажет первая генерация. При прямом ключе
  Google этот вопрос не возникает — там формат тот же, что был в n8n.
- **Имена моделей** взяты из n8n (`gemini-3-pro-image-preview`) и из
  документации шлюза (`google/gemini-2.5-flash-image-preview`). Google
  переименовывает preview-модели; менять — переменной окружения, не кодом.
  На живом ключе проверено, что `gemini-3-pro-image-preview` и
  `gemini-pro-latest` в списке доступных есть; более дешёвая альтернатива для
  картинок — `gemini-2.5-flash-image`.
- **Стоимость** генерации теперь идёт по ключу проекта, а не по ключу внутри
  n8n. Лимиты стоит проверить до массового прогона.
- **Ветки `marketplace`, `google-ads`, `youtube`, `web-banner`, `reels-cover`**
  идут в общую ветку промпта — как и в n8n, где `Switch1` разбирал только
  четыре типа, а остальные попадали в ветку по умолчанию.
