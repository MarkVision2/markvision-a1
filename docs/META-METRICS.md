# Откуда берутся цифры Meta

Короткая карта: как расход, лиды и CTR попадают в «Управление рекламой», Дашборд и Метрики,
и как проверить, что они сходятся с Ads Manager.

## Путь данных

```
Graph API v21.0 /act_<id>/insights
   ├─ meta-daily-sync      → cabinet_daily_insights (день × кабинет)
   └─ meta-structure-sync  → meta_campaign_daily / meta_creative_daily (день × кампания / объявление)
                                   ↓
        useMetaInsights / useMetaDashboard → страницы Ads, Dashboard, Metrics, Analytics
```

Оба синка ходят через общий модуль `supabase/functions/_lib/metaInsights.ts` — там живут
формулы и построение запроса, чтобы кабинет и креативы не считались по-разному.

Расписание (cron в БД, ключ `automation_settings.cron_secret`):

| Задача | Время (UTC) | Что делает |
| --- | --- | --- |
| `meta-daily-sync-daily` | 00:30 | вчерашний день по всем кабинетам |
| `meta-structure-sync-daily` | 01:30 | кампании, объявления и их дневные инсайты |

Вручную — кнопка «Получить статистику» в карточке кабинета (тот же код, период = выбранный месяц).

## Формулы

**Лиды.** Считаются ПО КАЖДОЙ КАМПАНИИ отдельно и потом складываются за день.
Внутри кампании берётся максимум по лид-событиям, включая начатые переписки:

```
lead, leadgen.other, onsite_conversion.lead_grouped,
offsite_conversion.fb_pixel_lead, onsite_web_lead,
onsite_conversion.messaging_conversation_started_7d
```

Складывать эти события нельзя: для кампании с целью «Лиды» и назначением в мессенджер
Meta кладёт один и тот же диалог сразу в несколько `action_type`. До сентября 2026 система
складывала «заявки» и «переписки» и завышала лиды примерно вдвое.

Кампания ведёт либо в переписку, либо в форму/на сайт, поэтому её максимум = реальное число
результатов, а сумма кампаний — честные лиды кабинета. Колонка `messages` показывает,
сколько из них пришло из переписок (она уже входит в `leads`, отдельно не прибавляется).

**CTR и CPC** — по кликам по ссылке (`inline_link_clicks`), как в основных колонках
Ads Manager. «Все клики» (`clicks`) тоже сохраняются, но включают лайки, комментарии и
клики по профилю — по ним CTR получался в разы выше метовского.

**Окно атрибуции** — `use_unified_attribution_setting=true`: Graph API отдаёт конверсии
в том же окне, что настроено у объявления. Без этого флага API считает в своём окне, и
цифры в интерфейсе не сходятся с тем, что видит пользователь в Meta.

**Валюта.** Не-KZT кабинеты пересчитываются в тенге по курсу НБК на день (`fx_rates`).
Если курса на день нет, берётся первый доступный курс периода — иначе один день оставался
в долларах и итог месяца складывал разные валюты.

## Как проверить сверку с Ads Manager

```bash
node scripts/meta-doctor.mjs --act act_XXXXXXXXXX --since 2026-09-01 --until 2026-09-30 --token <meta_token>
```

Скрипт ничего не меняет. Он показывает все `action_type` за период, лиды по кампаниям
(и сколько давала старая формула), CTR/CPC в обоих вариантах, разницу между окнами
атрибуции, а с `SUPABASE_SERVICE_ROLE_KEY` в окружении — ещё и сверку со строками
`cabinet_daily_insights`: расхождения по дням, дырки в синке, смешанные валюты.

Что смотреть, если цифры не сходятся:

- **Пусто за месяц** — синк не отрабатывал. Проверьте cron: `select jobname, command from cron.job where jobname like 'meta%'`
  (URL должен указывать на текущий проект) и `select * from ad_sync_runs order by created_at desc limit 20`.
- **Лиды не совпадают с Ads Manager** — сравните колонку «переписки» скрипта с графой
  «Начало переписки» в Meta; часовой пояс кабинета скрипт печатает первой строкой.
- **Дни съехали на один** — часовой пояс рекламного кабинета отличается от `Asia/Almaty`,
  по которому нарезаны лиды CRM. Итоги месяца при этом сходятся, посуточные CPL — нет.
