# ТЗ: подключение 100 Instagram-аккаунтов и автопубликация со статистикой

Составлено 06.09.2026 по итогам живой проверки прод-системы. Всё, что помечено
«проверено», проверено вызовами боевых API и запросами к прод-базе, а не взято из головы.
Документ рассчитан на исполнителя, который берёт задачу с нуля.

---

## 1. Цель

Подключить к MarkVision сеть из ~100 Instagram-аккаунтов так, чтобы платформа публиковала
в них через официальный API и собирала статистику по каждому посту.

**Решения заказчика:**
* Facebook не используем — подключение только через Instagram API with Instagram Login
  (`mode: "instagram"`, токен `IGAA…`). Последствия этого решения — в разделе 4.
* Сессии аккаунтов держим в **браузерных профилях с прокси** (не на облачных телефонах).

## 3. Факты, добытые проверкой — не перепроверять

Сэкономит исполнителю день работы.

### Про OAuth Instagram

* **Пачкой через Instagram Login подключить нельзя.** Нет сущности, которая держит аккаунты
  вместе, — это была роль Business Manager. Один аккаунт = один OAuth = одно нажатие
  «Разрешить». Ограничение Meta, не наше.
* **Аккаунт обязан быть Business или Creator.** Право `instagram_business_content_publish`
  личному профилю не выдаётся.
* **Instagram блокирует вход по паролю с незнакомого устройства.** Проверено на живой ссылке
  06.09.2026: клиент открыл приглашение на компьютере (Mac, IP Дубая через VPN) — Instagram
  показал «Мы заблокировали попытку входа», до нашего callback дело не дошло. Поймать это в
  коде нечем: `code` не выдан, редиректа нет, ошибку площадка не присылает.
* **Ключ к дешёвому подключению:** если открыть ссылку там, где Instagram уже залогинен,
  форму пароля не показывают вовсе — только экран согласия. Одно нажатие.
* **На телефоне ссылку перехватывает приложение Instagram.** Проверено: команда открыть
  `instagram.com` подняла не браузер, а приложение с залогиненным аккаунтом. Это и делает
  телефон надёжным маршрутом подключения.
* Токен `IGAA…` живёт **60 дней** и требует продления — в отличие от токена страницы Facebook,
  который не истекает. Механизм продления в проекте есть, но **на живых токенах ни разу не
  проверялся**.

### Про автоматизацию на облачных телефонах (PhoneGrid)

* `exeCommand` **возвращает stdout**, но не длиннее **5000 символов**. На этом построено всё
  остальное.
* `uiautomator dump` **читает разметку приложений** — поля логина, пароля, кнопки находятся с
  точными координатами. Реализовано в `supabase/functions/_lib/phonescreen.ts`.
* **Chrome содержимое веб-страницы в разметку не отдаёт** — виден только адресная строка.
  Проверены три обхода, все безрезультатно: флаг `--force-renderer-accessibility` (стоковый
  Chrome игнорирует), включение штатной службы спец-возможностей, и всё это **с root на
  телефоне**. **Вывод: автоматически заполнить OAuth-форму на телефоне нельзя.**
* Любой вызов Open API PhoneGrid стоит **~3 секунды** сам по себе — пустая команда `true`
  возвращается за 2952 мс. Кадр экрана собирается ~12 секунд. Видеопотока в Open API нет
  вовсе (все возможные endpoint'ы отвечают 404).
* Разрешение экрана у моделей **разное**: 1080×2340 и 1080×2400 — тап надо считать по
  реальному, иначе палец уезжает на десятки пикселей.
* `input text` принимает **только ASCII**, пробел передаётся как `%s`, строку обязательно
  брать в **одинарные** кавычки (в двойных шелл раскроет `$` и обратные кавычки).

### Про прокси

* Единственный прокси проекта `212.8.248.20` — это **адрес шлюза ротационного мобильного
  пула**, а не адрес выхода. Реальный выход за один день менялся: `93.157.181.157` →
  `176.64.54.149`; раньше наблюдались Уральск → Алматы → Костанай.
* Несколько телефонов, включённых **одновременно**, выходят с одного адреса — площадка видит
  один источник и связывает аккаунты. В разделе «Устройства» предупреждение уже стоит.
* **Одно устройство = один аккаунт**: закрыто уникальным индексом
  `publish_accounts_device_uniq`. Два аккаунта на одном телефоне площадка свяжет по отпечатку.

## 4. Чего стоит отказ от Facebook

Заказчик решение принял, но исполнитель должен понимать цену:

| | Через Facebook / Business Manager | Через Instagram Login |
|---|---|---|
| Подключение | **пачкой**, один вход администратора BM | по одному, 100 нажатий |
| Токен | `EAA…`, **не истекает** | `IGAA…`, **60 дней**, нужно продление |
| Требование к аккаунту | Business/Creator + страница FB | Business/Creator |
| Риск | бан приложения роняет всё сразу | то же |

Справочно: на 06.09.2026 Meta-токен проекта уже видит **27 страниц, из них 13 с привязанным
Instagram Business готовы к подключению одним нажатием** (@1metagarage 234k, @toyota_center_pavlodar
22k, @dagestan.topteam 14k и другие). Если решение по Facebook когда-нибудь пересмотрят —
это самый дешёвый путь, и он уже реализован (`publish-accounts` action `available` → `connect`).

## 5. Что делать

### Этап 0. App Review — начать первым, идёт неделями

Пока приложение Meta в режиме разработки, авторизоваться могут **только аккаунты с ролью в
приложении**. Сотню так не подключить в принципе.

1. Подать приложение на ревью на права `instagram_business_basic` и
   `instagram_business_content_publish`. Тексты формы, обоснования прав, сценарий
   демо-видео, инструкции проверяющему и чеклист — `docs/INSTAGRAM-APP-REVIEW.md`.
2. Подготовить демо-видео сценария подключения и публикации (по образцу
   `docs/TIKTOK-DEVELOPER-APP.md`, там это уже проходили для TikTok).
3. Публичные `/terms` и `/privacy` уже есть — `src/pages/Legal.tsx`; раздел
   `/privacy#instagram` — инструкция по удалению данных для поля Data deletion.

Состояние 06.09.2026: приложение `943753324681398` в режиме Live, но у обоих прав статус
«Готово к тестированию» — расширенного доступа нет, заявка не одобрена. Пока идёт ревью,
тестовая пятёрка подключается через роль «Instagram-тестировщик» в приложении.

**Приёмка:** приложение в статусе Live, у обоих прав «Расширенный доступ».

### Этап 1. Подготовка аккаунтов

1. Все 100 аккаунтов перевести в **Business или Creator**.
2. Для каждого зафиксировать: логин, пароль, TOTP-секрет двухфакторки, страна/город,
   к какому прокси относится. Хранить в менеджере паролей, **не в репозитории и не в базе
   платформы** — платформа паролей не хранит принципиально.

**Приёмка:** список из 100 строк, у каждой подтверждён тип аккаунта.

### Этап 2. Инфраструктура сессий: браузерные профили с прокси

**Маршрут выбран заказчиком.** Задача сводится к одному: получить 100 живых сессий
instagram.com — каждую под своим аккаунтом, со своим отпечатком и своим адресом выхода.
Профиль на аккаунт; куки живут месяцами, поэтому вход делается один раз, а подключение
и все будущие переподключения — уже без пароля.

Почему именно профили, а не телефоны: в настоящем браузере есть DOM, поэтому и вход, и
нажатие «Разрешить» **автоматизируются**. На облачном телефоне это невозможно — Chrome под
Android содержимое страницы наружу не отдаёт (проверено, раздел 3).

#### Инструмент

PhoneGrid MCP, уже подключён в проекте (`~/.claude.json`, сервер `phonegrid`). Возможности
проверены по схемам инструментов:

* `manage_browser` action `create` — **до 200 профилей за один вызов**. На профиль задаются:
  * `proxy` — свой на каждый: `proxyProvider` (http / https / socks5 / ssh, либо готовые
    интеграции Oxylabs, Luminati, ABCPROXY, LunaProxy, IPHTML, PiaProxy, 922S5, 360Proxy),
    `proxyIp`, `proxyPort`, `username`, `password`;
  * `operatorSystemId` — 1 Windows, 2 macOS, 3 Android, 4 iOS;
  * `browserTypeId` — 1 Chrome, 2 Firefox; `browserCore` — версия ядра (0 = автоподбор).
* `manage_browser` action `start` / `close` — поднять и погасить профиль по `envId`,
  `uniqueId` или `envName`. Есть `isHeadless`.
* `browser_operate` — управление активной страницей, по одному действию за вызов:
  * Playwright по CSS-селекторам: `navigate`, `click`, `fill`, `hover`, `select`, `scroll`,
    `press_key`, `drag`, `iframe_click`, `evaluate`;
  * AI-режим (Stagehand) на естественном языке: `act`, `extract`, `observe` — по описанию
    инструмента, хорош на сложных страницах и капчах;
  * чтение: `screenshot`, `get_html`, `get_text`.

Практический вывод: вёрстка Instagram меняется, поэтому вход и согласие писать **не на жёстких
селекторах, а через `act` / `observe`**, оставив CSS как запасной путь.

#### Что сделать

1. **Профили.** Создать по профилю на аккаунт. Отпечаток подбирать под легенду аккаунта:
   мобильная ОС для аккаунтов, которые вели с телефона, десктоп — для остальных. Имя профиля
   = @хэндл аккаунта, чтобы не перепутать при 100 штуках.
2. **Прокси.** Свой адрес на профиль, страна и оператор — как у аккаунта. Липкая сессия
   обязательна: прыгающий по городам IP для Instagram хуже стабильного (раздел 3).
   Ориентир — выделенный мобильный на 1–2 аккаунта; «все 100 на одном адресе» исключено.
3. **Первый вход — главный риск всего проекта.** Instagram блокирует вход по паролю с
   незнакомого устройства. Меры: прокси нужной страны, «прогретый» профиль (открыть
   instagram.com, полистать ленту до входа), вход не пачкой, а с паузами; TOTP-код
   двухфакторки подставлять из хранилища; при запросе подтверждения — подтверждать «Это был я»
   с телефона, где аккаунт уже залогинен.
4. **Проверка адреса.** После входа в каждом профиле убедиться, что выход идёт через нужный
   прокси: `browser_operate` action `navigate` на сервис определения IP + `get_text`.
   Совпадений адресов между профилями быть не должно.

**Приёмка этапа:** 100 профилей, в каждом выполнен вход в свой аккаунт, сессия живая
(перезапуск профиля не требует пароля), у каждого свой адрес выхода — подтверждено выгрузкой
«профиль → @хэндл → IP» без повторов.

*Резервный маршрут для отдельных случаев.* Если аккаунт наглухо не пускает в браузер,
подключение делается через облачный телефон: ссылку там перехватывает приложение Instagram,
пароль не спрашивают вовсе, нужно одно нажатие руками через окно телефона в платформе
(раздел «Устройства»). Для сотни не годится — телефон на аккаунт и поминутная оплата, — но
как аварийный путь работает.

### Этап 3. Конвейер подключения

Выполняется пачками по 20–30, полностью автоматизируемо.

1. **Выдать одноразовые ссылки.** `publish-accounts` action `connect_link_create`:
   `max_uses: 1`, короткий срок жизни, `platforms: ["instagram"]`. По ссылке на аккаунт.
2. **В каждом профиле:** `manage_browser start` → `browser_operate navigate` на
   `https://www.markvision.kz/connect/<токен>` → нажать «Подключить Instagram» →
   Instagram, видя живую сессию, покажет **только экран согласия, без пароля** →
   нажать «Разрешить» (`act`, с CSS как запасным путём) → дождаться возврата на нашу
   страницу с подтверждением → `manage_browser close`.
3. **Проверить результат** в `publish_accounts`: `auth_status = connected`, в `oauth_scope`
   присутствует `instagram_business_content_publish`, `connection_type = oauth`.
4. **Проставить пачке настройки** — группа, персона, часовой пояс, окно публикации, дневной
   лимит, разгон. Пресет на всю пачку в интерфейсе уже есть.

**Приёмка:** N аккаунтов в сетке со статусом «подключён», у каждого непустой `oauth_scope`
с правом публикации, ни одной ссылки не осталось неиспользованной.

### Этап 4. Проверить продление токенов, пока аккаунтов мало

**Критично и легко пропустить.** Токен живёт 60 дней. Если продление не работает, вся сеть
встанет разом через два месяца, и чинить придётся 100 подключений сразу.

1. На первых 3–5 подключённых аккаунтах вручную прогнать `publish-monitor` в режиме проверки
   токенов: `{ mode: "tokens", project_id, account_ids }` — режим принимает выбор аккаунтов и
   отдаёт `results` по каждому (`node scripts/instagram-connect.mjs tokens --batch <пачка>`).
2. Убедиться, что `token_refreshed_at` обновляется и `token_expires_at` уезжает вперёд.
   Свежему токену (моложе 24 часов) площадка продление не даёт — монитор пропускает его с
   причиной, это не ошибка; отказы продления попадают в `refresh_errors` и в `last_error`.
3. Проверить поведение на заведомо протухшем токене: аккаунт должен получить
   `auth_status: reconnect_required` и попасть в дайджест, а не молча перестать публиковать.

**Приёмка:** в `publish_accounts` у тестовых аккаунтов обновился `token_refreshed_at`;
на протухшем — корректный `reconnect_required` и уведомление.

### Этап 5. Живой прогон публикации и статистики

1. Залить ролик в «Видео» (или дождаться из контент-завода / монтажа / Reels — все три цеха
   теперь кладут рендер в `publish_videos`, шов `_lib/publishLibrary.ts`).
2. Разложить по группе (`plan_publish_slots`), дождаться воркера.
3. Проверить всю трассу задания: `queued → processing → published`, `external_post_id`
   заполнен, пост реально виден в аккаунте.
4. Через сутки убедиться, что появилась запись в `post_metrics` с контрольной точкой d1.

**Приёмка:** пост опубликован через API, метрики d1 собраны, цифры видны в «AI Content Analyst».

### Этап 6. Масштабирование

Повторить этапы 2–3 пачками по 20–30. После каждой пачки — сутки наблюдения за дайджестом
ошибок, прежде чем брать следующую.

## 6. Риски

| Риск | Последствие | Что делать |
|---|---|---|
| App Review не пройден | сотню не подключить вообще | начать первым делом, этап 0 |
| Все аккаунты на одном приложении | бан роняет всю сеть | разнести по 20–30 |
| Ферма однотипных аккаунтов | Meta блокирует приложение | разные приложения Meta, реалистичные профили |
| Продление токенов не работает | вся сеть встанет через 60 дней | этап 4, проверить на первых аккаунтах |
| Мало прокси | площадка связывает аккаунты между собой | выделенный мобильный на 1–2 аккаунта |
| Личные профили вместо Business | право на публикацию не выдаётся | этап 1 |

## 9. Инструменты под это ТЗ

Сделаны по итогам ТЗ, чтобы этапы 2–5 не делались руками и принимались проверяемо.

* **Скилл `instagram-connect`** (`.claude/skills/instagram-connect/SKILL.md`) — порядок
  действий для Claude-сессии с MCP `phonegrid`: создание профилей, проверка адреса выхода,
  прогрев и вход с TOTP, конвейер «ссылка → согласие → возврат», ворота и паузы. Команда
  «подключи пачку аккаунтов» = этот скилл.
* **`scripts/instagram-connect.mjs`** — всё, что идёт через backend с ключом автоматизации
  (`AUTOMATION_KEY` в `.env`); реестр пачки `work/ig-connect/<batch>.json`, в git не попадает:

  | Команда | Этап | Что делает |
  |---|---|---|
  | `links --project … --handles @a,@b --batch …` | 3 | одноразовая ссылка на аккаунт (`max_uses 1`, только Instagram) |
  | `ip --batch … --set @a=IP --profile @a=envId` | 2 | реестр «профиль → @хэндл → IP», повторы адресов по всем пачкам; код 0 = приёмка |
  | `status --batch …` | 3 | по хэндлу: ссылка использована, `auth_status`, право публикации в `oauth_scope`, `connection_type`; код 0 = приёмка |
  | `preset --batch … --group … --timezone … --window … --daily-limit … --ramp` | 3 | настройки на всю пачку (`accounts_bulk_update`) |
  | `tokens --batch …` | 4 | `publish-monitor mode=tokens` по аккаунтам пачки: продлён ли, срок, живость, `auth_status` |

* **`publish-monitor` режим `tokens`** принимает `project_id` / `account_ids`, отдаёт `results`
  по каждому аккаунту, не глотает отказ продления и помечает мёртвый токен
  `auth_status reconnect_required` с уведомлением — раньше режим ставил только
  `status token_expired`, и сетка показывала «подключён» у аккаунта, который не публикует.

  `_lib/publishTokenRefresh.ts` с тестами `_tests/publishTokenRefresh_test.ts`.
